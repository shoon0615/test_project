## 1. 개요

### 1.1 목적

v1.0.1에서는 기존 Team CRUD 요구사항을 유지하되, 기술 스택과 개발 품질 기준을 높인다.

기존 v1.0.0은 정적 HTML/CSS/JavaScript와 `localStorage` 기반이었다. v1.0.1은 Next.js, mock API, TDD, QA를 포함해 실제 프론트엔드 개발 흐름에 더 가까운 구조로 만든다.

### 1.2 배경

팀 CRUD 기능 자체는 동일하지만, 학습 목표가 단순 구현에서 “테스트 가능한 구조”, “API 통신 기반 상태 관리”, “QA 가능한 기능 단위”로 확장되었다.

따라서 v1.0.1은 서버less 정적 앱이 아니라, mock API를 사용하는 프론트엔드 애플리케이션으로 계획한다.

## 2. 버전 업그레이드 방향

| 항목 | v1.0.0 | v1.0.1 |
|------|--------|--------|
| 프론트엔드 | HTML/CSS/JavaScript | Next.js |
| 데이터 저장 | `localStorage` | `json-server` 또는 mock API |
| 데이터 접근 | 브라우저 내부 저장 | API client 계층 |
| 테스트 | 수동 확인 중심 | TDD 기반 단위/컴포넌트 테스트 |
| QA | 간단한 브라우저 확인 | 기능 시나리오 기반 QA |
| 문서 | Starter 수준 | 설계, 테스트, QA 기준 포함 |

## 3. 목표

### 3.1 주요 목표

- [ ] Next.js 기반 Team CRUD 화면을 만든다.
- [ ] 팀 생성, 조회, 수정, 삭제 요구사항을 유지한다.
- [ ] `json-server` 또는 mock API를 사용해 데이터 저장 흐름을 구현한다.
- [ ] API client 계층을 분리한다.
- [ ] TDD 방식으로 핵심 로직과 UI 동작을 검증한다.
- [ ] QA 시나리오 문서를 작성하고 확인 기준을 만든다.
- [ ] 기존 v1.0.0 문서는 수정하지 않는다.

### 3.2 하지 않을 일

- 실제 운영 DB를 연결하지 않는다.
- 인증, 권한, 사용자 역할 기능은 포함하지 않는다.
- 배포 자동화는 이번 버전의 필수 범위로 보지 않는다.
- 실시간 협업 기능은 포함하지 않는다.

## 4. 범위

### 4.1 포함 범위

- 팀 목록 페이지
- 팀 생성 폼
- 팀 수정 폼 또는 수정 모드
- 팀 삭제 기능
- 검색 기능
- 상태 필터 기능
- 입력 검증
- mock DB 데이터 구조
- API client
- 테스트 계획
- QA 체크리스트

### 4.2 제외 범위

- 실제 백엔드 서버 개발
- 실제 RDBMS 또는 클라우드 DB 연결
- 로그인과 세션 관리
- 권한별 접근 제어
- 운영 모니터링

## 6. 비기능 요구사항

| 항목 | 기준 | 확인 방법 |
|------|------|-----------|

## 7. 기술 스택 후보

| 영역 | 선택 후보 | 비고 |
|------|-----------|------|
| 앱 프레임워크 | Next.js | App Router 기준으로 설계 |
| 언어 | TypeScript | 타입 안정성을 위해 권장 |
| mock DB | `json-server` | REST API 흐름 학습에 적합 |
| 대체 mock | MSW 또는 Next.js Route Handler mock | 테스트와 개발 환경 분리에 유리 |
| 테스트 러너 | Vitest 또는 Jest | Next.js 설정과 호환성 검토 필요 |
| 컴포넌트 테스트 | React Testing Library | 사용자 행동 중심 테스트 |
| E2E/QA | Playwright | 주요 CRUD 시나리오 검증 |

## 9. TDD 계획

### 9.1 우선 테스트 대상

- 팀 입력값 검증 함수
- 팀 목록 검색 함수
- 상태 필터 함수
- API client의 CRUD 요청 함수
- 팀 폼 제출 동작
- 수정 모드 전환 동작
- 삭제 확인 후 목록 갱신 동작

### 9.2 테스트 작성 순서

1. 데이터 타입과 검증 함수 테스트를 먼저 작성한다.
2. 검색과 필터 같은 순수 함수 테스트를 작성한다.
3. API client mock 테스트를 작성한다.
4. UI 컴포넌트 테스트를 작성한다.
5. QA 시나리오 또는 E2E 테스트를 작성한다.

## 10. QA 계획

| 시나리오 | 확인 내용 |
|----------|-----------|
| 팀 등록 | 필수값 입력 후 팀이 목록에 추가되는지 확인 |
| 입력 검증 | 빈 팀 이름, 잘못된 인원 수가 차단되는지 확인 |
| 팀 수정 | 수정 후 목록 값이 바뀌는지 확인 |
| 팀 삭제 | 삭제 확인 후 목록에서 제거되는지 확인 |
| 검색 | 검색어와 일치하는 팀만 보이는지 확인 |
| 상태 필터 | 선택한 상태의 팀만 보이는지 확인 |
| API 실패 | mock API 실패 시 오류 메시지가 보이는지 확인 |

## 11. 위험 요소와 대응

| 위험 요소 | 영향도 | 가능성 | 대응 |
|-----------|--------|--------|------|
| Next.js와 json-server를 동시에 실행해야 해 초보자에게 복잡할 수 있다. | 중간 | 중간 | 실행 명령과 역할을 문서에 분리해서 적는다. |
| mock DB와 실제 DB의 차이를 혼동할 수 있다. | 중간 | 중간 | mock DB는 개발용 API 대체 수단임을 명확히 한다. |
| TDD 범위가 넓어져 구현 속도가 느려질 수 있다. | 중간 | 높음 | 검증 함수, API client, 주요 UI 흐름부터 우선 테스트한다. |
| QA와 테스트가 중복될 수 있다. | 낮음 | 중간 | 테스트는 자동 검증, QA는 사용자 시나리오 확인으로 역할을 나눈다. |
